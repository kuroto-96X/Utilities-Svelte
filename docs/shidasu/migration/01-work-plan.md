# Shidasu Godot移植プロジェクト: 作業順計画(手順1)

## Context

現在SvelteKit + Svelte5(TypeScript)で実装されている「Shidasu」(Balatro風トランプソリティア型ローグライク、`/game/shidasu`)を、Godotエンジンに移植してSteam向けPCゲームとして販売する計画。

進め方は3段階:
1. **作業順の計画を立てる(今回はこれのみ)**
2. 作業順ごとのAI指示プロンプトを作成する(次回以降)
3. 作成したプロンプトを順にAIで実行する(次回以降)

作業はすべてAIエージェントに任せる前提。成果物(この計画書・今後作成する資料・プロンプト)はすべて `docs/shidasu/migration/` に保存する。

### 確定済みの移行方針(ユーザー確認済み)
- Godot実装言語: **GDScript**
- コンテンツスコープ: **現状の内容を完全移植するのみ**(スプレッド10種・護符99種・秘儀24種・天啓28種・レリック10種・妨害32種)。ロードマップ上の未着手拡張は対象外
- Steam向け機能: **最小限**(実績・クラウドセーブ等は初期スコープ外、後続フェーズ扱い)
- ビジュアル/オーディオ: **強化する**(現状は画像アセットなし・CSS/Unicode文字描画のみ、音声演出は皆無。Godot版では新規に商用品質のグラフィック・SE/BGMを制作/調達する)

### 調査で判明した重要な前提
- 既存ドキュメント `docs/shidasu/shidasu-current-rules.md` は**実装より古い**(スプレッドを2種としか書いていないが、コード上は10種実装済み。護符も件数の記載が古い)。→ **移植の正はコード(`engine.ts`等)と`shidasu.config.json`であり、既存docsを鵜呑みにしない。** これを踏まえ、資料化フェーズで最新化する。
- ロジック層(`src/lib/game/shidasu/`)はSvelte非依存の純粋関数型TypeScript(`RunState`/`WaveState`を引数に取り新しい状態を返すイミュータブル設計)。UI層は`applyPlayCard`等を呼んで返り値を`$state`に代入するだけ。この分離構造はGodot移植でも踏襲すべき優れた設計。
- UI演出面では「移動先の常設UI要素がアニメーション完了前の状態を先出ししてしまう」バグが繰り返し発生し、その都度「表示専用`$state`スナップショット変数+ガードフラグ」という対策を個別実装している(技術的負債としてCLAUDE.mdにも明記)。Godot移植では`AnimationPlayer`/`Tween`のシグナルベースの仕組みで構造的に解消する。

## リポジトリ構成・開発環境(ユーザー確認済み)

### 方針
- Godotプロジェクトは既存の`Utilities-Svelte`とは**完全に別管理**にする
  - 配置場所: `Utilities-Svelte`と兄弟階層の別フォルダ(例: `../Shidasu-Godot/`)に新規作成
  - gitリポジトリも別管理(`Utilities-Svelte`のリポジトリとは独立した新規リポジトリ)
- VSCode上で、Godotプロジェクトと`Utilities-Svelte`の**両方をAI(Claude)が閲覧しながら作業できる環境**を用意する

### 実現方法
- VSCodeの`.code-workspace`によるマルチルートワークスペースで、Godotプロジェクトフォルダと`Utilities-Svelte`フォルダの両方を登録する
- Claude Code側も同様に、Godotプロジェクトを起点にしつつ`Utilities-Svelte`を追加の作業ディレクトリとして登録する(現在のセッションで`docs/superpowers/specs`が追加ディレクトリとして見えているのと同じ仕組み)

### 作業分担(AI代行可否)

| 作業 | 代行可否 |
|---|---|
| 新規フォルダ作成・Godotプロジェクト雛形(`project.godot`等)作成 | 可能 |
| `.code-workspace`ファイル作成 | 可能 |
| ローカルgitリポジトリの新規init・`.gitignore`設定 | 可能 |
| Claude Codeへの追加作業ディレクトリ登録(設定・起動オプション) | 設定内容は用意できるが、反映にはセッション再起動等ユーザー操作が必要になる場合あり |
| リモートリポジトリの新規作成(GitHub等)・push | 技術的に可能だが、共有リソースを作る操作のため実行前に必ずユーザーに確認する |
| Godotエディタ本体のインストール・起動 | 不可(GUIアプリのインストール・操作はユーザー側で実施) |

## フェーズ計画(全16フェーズ)

各フェーズは「後続でAI実行用の1プロンプトに落とし込める単位」を意識して区切ってある。護符99種のようにコンテンツ量が多い箇所は、実行時にさらに分割してもよい前提。

### フェーズ1: 現状仕様の資料化(移植用リファレンス作成)
**目的**: Web版ソースを読まなくても正確に移植できる仕様書を作る。既存docsは古いため、コード+JSONを正として作り直す。

**作業内容**:
- `shidasu.config.json`・`types.ts`・`engine.ts`を突き合わせ、現行仕様書を実装に合わせて最新化(スプレッド10種・護符99種・秘儀24種・天啓28種・レリック10種・妨害32種)
- 護符/秘儀/天啓/レリック/妨害/役/スプレッドそれぞれの「ID・名称・効果ロジックの自然文記述・関連パラメータ名・依存State」を一覧化したコンテンツカタログ(Markdown表 or JSON)を作成
- スコア計算パイプラインの実装順序を明文化
- 乱数(`createRng`、mulberry32型PRNG)の扱いをGodotでどうするか論点整理(結論はフェーズ2)
- `PlayArea.svelte`の技術的負債(表示専用スナップショットパターン)の発生箇所・原因を棚卸し

**成果物**: `docs/shidasu/migration/`配下に、最新化ルール仕様書・全コンテンツカタログ・スコア計算パイプライン仕様・技術的負債棚卸しメモ
**依存**: なし(起点)
**参照ファイル**: `src/lib/game/shidasu/types.ts`, `params.ts`, `shidasu.config.json`, `engine.ts`, `docs/shidasu/shidasu-current-rules.md`, `shidasu-glossary.md`

### フェーズ2: Godotプロジェクトの基盤構築
**目的**: プロジェクト構成・状態管理パターンを決定し、以後の全フェーズの土台を作る。

**作業内容**:
- プロジェクトのフォルダ構成方針(`logic/`/`scenes/`/`data/`/`assets/`)決定
- **状態管理パターンの移植方針決定**: GDScriptオブジェクトは参照型のため、Web版の「引数を取り新しいオブジェクトを返す」設計を単純移植すると意図せぬ書き換えが起きる。`RefCounted`ベースのステートクラス+明示的な`duplicate_state()`(ディープコピー)を規約化し、「更新関数は必ずコピーを返す」というWeb版の設計思想自体は踏襲する
- ロジック層(Node非依存の素のGDScriptクラス)とUI層(シーン・ノード)の分離方針決定
- 乱数方針決定: 決定論的互換は不要なためGodot標準RNGへの置き換えを推奨。ただしシード指定によるリプレイ/テスト再現性は維持
- GDScriptコーディング規約(命名・型付け・enum方針)決定

**成果物**: Godotプロジェクト雛形、状態管理サンプル実装、アーキテクチャ決定記録
**依存**: フェーズ1
**注意点**: 最も構造的に作り直すべき部分。ここで規約を誤ると以後全フェーズで状態共有バグが頻発するリスクが高い
**参照ファイル**: `types.ts`(RunState/WaveState全体), `engine.ts`(更新関数の呼び出しパターン)

### フェーズ3: コアデータモデル・パラメータ/コンテンツデータの移植

- コンテンツカタログを元に、各アイテムのID一覧・メタデータを定義

**成果物**: GDScript型定義一式、JSONローダー、コンテンツID・メタデータ一覧
**依存**: フェーズ1, 2
**参照ファイル**: `types.ts`, `params.ts`, `shidasu.config.json`, `items.ts`, `rites.ts`, `revelations.ts`, `relics.ts`, `sabotage.ts`, `roles.ts`

## フェーズ間の依存関係

```
フェーズ1(資料化)
   ├─→ フェーズ2(Godot基盤)→3(データモデル)→4(進行フロー)→5(スコアリング)
   │      →6(護符)→7(秘儀/天啓)→8(神託/レリック/ショップ)→9(妨害/スプレッド統合)
   │      ├─→ フェーズ10(テスト整備。各フェーズ内でも並行実施推奨)
   │      └─→ フェーズ11(UI①)→12(UI②)→13(演出再設計)→15(オーディオ、一部並行可)
   └─→ フェーズ14(ビジュアルアセット) ※フェーズ2〜10と並行可、フェーズ11着手前に一定量必要

フェーズ16(パッケージング) ← 上記すべて完了後
```

**直列必須**: フェーズ2(状態管理パターン決定)→3→4→5→6〜9は、下位フェーズの構造決定が上位の実装方針を左右するため順序厳守。
**並行可能**: フェーズ14(アセット制作)はフェーズ1完了後すぐ着手しフェーズ2〜10と並行進行可。フェーズ15のBGM制作もフェーズ1完了後から並行着手可。
