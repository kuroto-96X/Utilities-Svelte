# フェーズ11: UI実装①(タイトル・スプレッド選択・基本画面構成)

> このプロンプトは、Shidasu(Balatro風トランプソリティア型ローグライク)をGodot(GDScript)へ移植し、Steam向けPCゲームとして販売するプロジェクトの一部です。Godotプロジェクトは元のWebリポジトリ(Utilities-Svelte)とは別管理ですが、VSCodeのマルチルートワークスペースにより両方のファイルを参照できます。
>
> 着手前に必ず読むこと:
> - `Utilities-Svelte/docs/shidasu/migration/01-work-plan.md`(全体計画)
> - フェーズ9の成果物(妨害・スプレッドを含むロジック層が、UIなしで1Run分シミュレートできる状態になっていること。本フェーズはこのロジック層を初めてUIから呼び出す)
> - フェーズ14のアセット状況(未着手・仮素材のみでも進めてよい。本フェーズの依存は「アセットが存在すること」ではなく「アセットが無くても仮の四角形やUnicode文字で進められる」という前提)

## 目的

ゲーム全体のシーン構成(`RunPhase`ごとの画面切り替えの骨格)と、プレイヤーが最初に触れる「入口」画面(タイトル・スプレッド選択)を実装する。

## 前提・依存

- 依存: フェーズ9(妨害・スプレッドを含むロジック層一式)。
- 依存: フェーズ14の一部アセット(仮素材可)。カード画像・背景等が無くても、色付きの`ColorRect`やUnicode文字描画で代替して進めてよい。
- **管理画面(`/admin/shidasu*`)・`DebugPanel.svelte`は移植対象外。** Web版にはパラメータ調整用の管理画面やデバッグパネルが存在するが、これらはコンテンツ管理用のツールであり、Steam版の対象範囲(プレイヤー向けゲーム本体)には含めない。

## 作業内容

### 1. フェーズ遷移統括ロジックの再設計

Web版(`+page.svelte`)は`run.phase`(`RunPhase`型)の値によって`{#if}`/`{:else if}`チェーンで表示する画面ブロックを切り替えている。`RunPhase`は以下の11種類。

```
'title' | 'playing' | 'shop' | 'itemSelect' | 'riteSelect' | 'revelationSelect'
| 'oracleSelect' | 'cardSetSelect' | 'continueChoice' | 'allClear' | 'gameOver'
```

これをGodotでは「`RunPhase`(またはenum)の値に応じて、対応するシーン/`Control`ノードの表示・非表示を切り替える」という構造で再設計する。具体的には以下を決定・実装すること。

- ルートとなるシーン(例: `Game.tscn`)の下に、各フェーズに対応する`Control`ノード(またはシーンインスタンス)を子として並べ、現在の`RunPhase`と一致するノードだけを`visible = true`にする、という単純な排他表示の仕組みを基本方針とする。Web版の`{#if}`チェーンの直接的な対応物であり、過度に複雑な状態遷移フレームワークを新規導入する必要はない。
- Web版には`run.phase`だけでは表現しきれない**UI専用のローカルフラグ**が複数存在し、素直に1対1変換すると見落としやすい。以下は必ず踏襲するか、Godot側でも同等の分離を意識すること。
  - `showStageScreen`(`+page.svelte`93行目付近): 「Wave開始前のステージ確認画面(3つの星のプレビュー・スキップ/リロールボタン)」を表示するかどうかは`run.phase === 'shop'`だけでは決まらず、このローカルstateと組み合わせて判定している。`run.phase`が`'shop'`になった直後に自動でこの画面を出すか、ショップ画面自体を出すかを`showStageScreen`で切り替える設計であり、`$effect`(96〜105行目)で「shopフェーズに切り替わった直後だけリセットする」という順序依存のロジックが入っている。この「フェーズ値だけでなく遷移元(直前のフェーズ)によって挙動を変える」という考え方はGodot側でも保持すること(例えば「直前がtitleだったか」を状態機械側で覚えておく)。
  - `revelationPreviewWave`: `revelationSelect`フェーズは`{:else if}`チェーンの一部としてではなく、常時マウントされた本番プレイ画面の**上に固定オーバーレイとして重ねる**という特殊な構成になっている(878〜908行目のコメント参照。理由は「`{:else if}`で切り替えると本番画面がアンマウントされ、復帰時に配布アニメーションが誤発火するため」)。Godotでは`Control`の表示/非表示だけで済む(アンマウント問題が原理的に発生しない)ため、この回避策自体を移植する必要はないが、「天啓選択中も本番の場札状態を裏で保持しておく」という要件自体は再現すること。
- 本フェーズでは、上記の骨格(`RunPhase`→表示ノードの対応、`showStageScreen`相当のUI専用フラグ)を用意した上で、**`title`フェーズと`itemSelect`等の各選択画面については以下の範囲で実装する**。
  - `title`(スプレッド選択含む): 本フェーズで完全実装する(下記2.)。
  - `playing`/`shop`/`itemSelect`/`riteSelect`/`revelationSelect`/`oracleSelect`/`cardSetSelect`/`continueChoice`/`allClear`/`gameOver`: 本フェーズでは「対応するノードが存在し、正しいタイミングで表示/非表示が切り替わる」ところまでを作れば十分(中身は仮のプレースホルダー、または最小限のテキスト表示でよい)。中身の作り込み(場札操作・ショップ購入UI・各種選択UIの実装)はフェーズ12の担当。
  - 特に`title`→`handleStartWithSpread`相当の処理(`beginRun`呼び出し)の直後に表示される「ステージ確認画面」(`+page.svelte`1285〜1340行目、3つの星のプレビュー・スキップ/リロールボタンを含む)は、`run.phase === 'shop'`のサブ状態として存在するため、フェーズ12(ショップ画面の担当フェーズ)と地続きの実装になる。本フェーズでは「タイトルのスタートボタンを押すと、この画面(仮の中身でよい)へ遷移する」ところまでを繋げれば`成果物`の「タイトル→スプレッド選択→ゲーム開始までの画面遷移」を満たしたことになる。

### 2. タイトル画面・スプレッド選択画面の実装

Web版の実装(`+page.svelte`772〜851行目)を踏まえ、以下の要素を実装する。

- タイトルロゴ・キャッチコピー・簡単な操作説明テキスト(Web版は「ランクの±1を連鎖で取ってスコアを稼ぐ」等の4行程度の説明。文言はそのまま踏襲してよい)。
- **スプレッド選択カルーセル**: `SpreadId`10種(`fool`/`moon`/`pope`/`empress`/`magician`/`justice`/`lovers`/`emperor`/`wheelOfFortune`/`strength`)を、前後ボタン(◀▶)で1つずつ切り替えながら選ぶUI。
  - 現在選択中のインデックス(Web版の`selectedSpreadIndex`)を保持し、◀▶で`(index - 1 + 10) % 10`/`(index + 1) % 10`によりループさせる(`goToPrevSpread`/`goToNextSpread`、237〜242行目)。
  - 各スプレッドの`name`(名称)・`desc`(説明文)を表示する。データは`ShidasuParams.spreads[spreadId]`(フェーズ3で移植済みのJSONローダー経由)から取得する。
  - 現在位置を示すドットインジケーター(10個の点、選択中のみ強調)。
  - 切り替え時のフェードトランジション。**Web版では「フェード中に前後のスプレッドの内容が一瞬混ざって見える」「フェード中に高さが変わってガタつく」というバグが直近で2件発生し修正されている(コミット`efed337`「フェード中に別スプレッドの内容が表示されるバグを修正」、`32330b2`「フェード中に表示が縦にずれるバグを修正」、`ef68130`「説明カードの高さを最長の説明文に合わせて実測固定」)。** これはWeb版がCSSの`{#key}`ブロック+`position:absolute`+高さ不定のブロック要素という組み合わせで発生した問題であり、Godotで同種のUIを作る場合は原因が異なる可能性が高いが、念のため実装後に「切り替えアニメーション中に前後の内容が混ざらないか」「切り替え中にレイアウトが上下にずれないか」を目視確認すること。対策の考え方としては、Web版が最終的に採用した「最長の説明文に合わせてカードの高さを固定する」方式(全スプレッド分を一度重ねて描画し最大高さを実測する、`measuredSpreadCardHeight`)が参考になるが、Godotでは`Container`が持つ最小サイズ計算の仕組みを使い、10種の説明文のうち最大の高さに合わせてカードの最小高さを固定する、という形で同等の効果をより単純に実現できる可能性が高い。Web版のような「画面外に一度描画して`offsetHeight`を実測する」という回避策(773〜800行目)は、解像度非依存レイアウト(下記3.)への作り直しに伴い、Godot側では不要になる可能性が高いので、まずGodot標準のレイアウト機構で解決できないか検討してから実装すること。
- スタートボタン: 押すと選択中の`spreadId`で`beginRun`相当の処理を呼び出し、ステージ確認画面(または仮のプレースホルダー)へ遷移する(`handleStartWithSpread`、244〜247行目)。

### 3. 解像度非依存レイアウトへの作り直し

Web版は**スマホ固定幅480px**を前提にしたレイアウト(ルート要素に`max-width:480px`、769行目・884行目・1345行目など複数箇所で固定値を直書き)になっている。Steam版はPC向けで様々な解像度・ウィンドウサイズに対応する必要があるため、単純な移植ではなく**構造的な作り直しが必要**。

- Godotの`Control`ノード+アンカー/コンテナ(`CenterContainer`/`VBoxContainer`/`MarginContainer`等)を使い、画面サイズに応じて要素が適切に配置・スケールされるレイアウトを設計する。
- 「本来はスマホ1カラム縦積みだったUIを、PC画面でどう配置し直すか」は本フェーズの設計判断に委ねられる(例: 中央に固定幅カラムを維持しつつ余白を広げる、横幅を活かして左右に情報を分散する、等)。少なくとも「ウィンドウをリサイズしても要素が崩れない/はみ出さない」ことを確認できるレイアウトにすること。
- この解像度非依存レイアウトの方針は、本フェーズで作るタイトル/スプレッド選択画面だけでなく、フェーズ12以降の全画面に適用される土台になる。ここで場当たり的な固定ピクセル配置を作ってしまうと以後のフェーズ全部に影響するため、コンテナ/アンカーベースの設計を最初にきちんと固めること。

## 注意点

- 本フェーズは画面遷移の骨格と入口画面が対象であり、場札操作・ショップ購入・各種選択UIの中身はフェーズ12の担当。中身を作り込みすぎて工数を先食いしないこと(仮のプレースホルダーで十分)。
- Web版のレイアウトはスマホ480px固定を前提にした設計上の負債であり、そのまま移植するとPC画面で不自然に小さく中央寄せされるだけの見た目になる。「移植」ではなく「作り直し」であることを常に意識すること。
- スプレッド説明カードのちらつき系バグはWeb版で複数回修正が入った箇所であり、Godot移植でも似た罠(切り替えアニメーション中の一瞬の表示崩れ)が起きやすい。実装後に必ず目視確認を行うこと。
