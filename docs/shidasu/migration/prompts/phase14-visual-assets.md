# フェーズ14: ビジュアルアセット制作・組み込み

> このプロンプトは、Shidasu(Balatro風トランプソリティア型ローグライク)をGodot(GDScript)へ移植し、Steam向けPCゲームとして販売するプロジェクトの一部です。Godotプロジェクトは元のWebリポジトリ(Utilities-Svelte)とは別管理ですが、VSCodeのマルチルートワークスペースにより両方のファイルを参照できます。
>
> 着手前に必ず読むこと:
> - `Utilities-Svelte/docs/shidasu/migration/01-work-plan.md`(全体計画)
> - `Utilities-Svelte/docs/shidasu/migration/`配下にあるフェーズ1の成果物(コンテンツカタログ。護符/秘儀/天啓/神託/レリック/妨害/役/スプレッドのID・名称・モチーフが一覧化されている。ファイル名は実際に生成されたものを確認すること)
> - `Utilities-Svelte/docs/shidasu/shidasu-glossary.md`(世界観・用語集)

## 目的

Web版は画像アセットを一切使わず、CSS/Unicode文字のみで描画する「ノーアセット」実装だった。Godot版はSteam商用品質のビジュアルへ強化する方針(ユーザー確認済み)であり、本フェーズでカード・UI・背景のアセット一式をゼロから制作し、Godotプロジェクトに組み込む。

## 前提・依存

- 依存: フェーズ1(コンテンツカタログ・モチーフ理解)のみ。**フェーズ2〜10(ロジック層の移植)とは並行実施可能**なので、フェーズ1完了後はロジック側の進行を待たずできるだけ早期に着手してよい。
- 後続への影響: フェーズ11(UI実装①)・フェーズ12(UI実装②)・フェーズ13(演出再設計)は、本フェーズの成果物(または暫定的な仮素材)に依存する。アセットが未完成のままUI実装を止めないよう、仮素材(プレースホルダー)を先に用意し、本番アセットへの差し替えを後追いで行う進め方でもよい。
- 本フェーズはコード実装を主目的としない。GDScriptの実装詳細よりも「何を作るか」「Godotのどこに配置するか」「後続フェーズとどう連携するか」を重視すること。

## 世界観・アートディレクションの方針

Shidasuのゲーム内アイテム体系は、それぞれ固有のモチーフを持つ占術・易学の世界観に基づいている。ビジュアル制作にあたっては、この世界観に沿ったアートディレクションを統一的に適用する。

- **護符(Talisman)**: 北欧ルーン文字をモチーフにしたデザイン
- **天啓(Revelation)**: 二十八宿(中国天文学の星座区分)をモチーフにしたデザイン
- **神託(Oracle)**: 六十四卦(易経)をモチーフにしたデザイン
- **スプレッド(Spread)**: 大アルカナ(タロット)をモチーフにしたデザイン

各カテゴリのモチーフは、フェーズ1のコンテンツカタログに記載されている個々のアイテム名・効果と整合させること(例: 特定の護符名がある北欧神話由来のルーン名を想起させる場合、そのルーンの意匠を反映する、等)。秘儀(Rite)・レリック(Relic)・妨害(Sabotage)についても、上記4カテゴリとトーンが浮かないよう、`shidasu-glossary.md`の用語・世界観設定と整合する意匠に揃える。

## 作業内容

### 1. カードデザイン

- スート4種(通常のトランプスート相当。`Utilities-Svelte`のロジック層の`Suit`型定義を`types.ts`で確認し、正確な種別を把握する)+ワイルドの表面デザイン
- ランク1〜13(A〜K相当)の表面デザイン。スート×ランクの組み合わせ全パターンを設計できるよう、共通レイアウト(数字/記号配置ルール)を先に決め、そのルールに沿って量産する
- 裏面デザイン(1種、ゲーム全体で共通)

### 2. UI全体のビジュアルコンセプト

- 上記「世界観・アートディレクションの方針」に基づき、護符バッジ・秘儀/天啓/神託のカード風UI・レリックバッジ・スプレッド選択画面のカードイラスト等、カテゴリごとの視覚的アイデンティティを確立する
- フォント・配色・枠装飾など、UI全体で共通のビジュアルボキャブラリ(トーン&マナー)を定義する

### 3. 背景・エフェクト素材

- タイトル画面・プレイ画面・ショップ画面・結果画面それぞれの背景
- フェーズ13(演出再設計)で使うパーティクル/エフェクト用のテクスチャ素材(光る・散る・シェイクを強調する装飾等)。フェーズ13の演出設計(共通パターン)がどのような差し替え可能な見た目を要求するかは、フェーズ13着手時に連携が必要になる場合がある

### 4. Godotへのインポート

- Godotプロジェクトの`assets/`(または合意されたフォルダ構成、フェーズ2のフォルダ構成方針を参照)配下に、カテゴリごとに整理して配置する(例: `assets/cards/`, `assets/ui/talisman/`, `assets/ui/revelation/`, `assets/ui/oracle/`, `assets/backgrounds/`)
- ファイル命名規則をロジック層のID(フェーズ3で定義するGDScriptのenum/ID)と対応付ける形で統一する。例えば護符ID`xxx`の画像は`talisman_xxx.png`のように機械的に対応が取れる命名にし、後続フェーズ(UI実装)でIDから画像パスを自動解決できるようにする
- Godotのインポート設定(テクスチャ圧縮・フィルタ有無・アトラス化の要否)を決定し、パフォーマンス上問題がないことを確認する

## 注意点

- 手戻り防止のため、フェーズ1完了後できるだけ早期に着手する(フェーズ11〜13が本フェーズの成果物待ちで止まらないようにする)
- 全アセットが揃うまでUI実装(フェーズ11・12)を止めないこと。仮素材(プレースホルダー、単色矩形+テキストラベル等)を先に用意し、本番アセットが揃い次第差し替える段階的な進め方を推奨する
- コンテンツカタログにあるアイテム数(護符99種等)は多いため、量産作業は複数パスに分割してよい(フェーズ6の護符効果移植と同様の考え方)
