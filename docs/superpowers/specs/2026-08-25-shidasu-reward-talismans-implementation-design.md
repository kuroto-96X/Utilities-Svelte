# 報酬増加系護符 実装設計

## 背景・目的

`docs/shidasu/shidasu-reward-talismans-candidates.md`で検討してきた報酬増加系護符の候補のうち、方向性1(特定行動で自分自身の売値を増加、22候補)と、方向性に依存しない候補(8候補)を対象に、実際に実装する24件の護符を確定する。方向性2(プレイ中に特定条件を満たした場合に即時報酬)・方向性3(秘儀・天啓・神託使用時にキャッシュバック)は引き続き未着手だが、方向性非依存候補のうち4件はそのまま方向性2の内容と一致するため、本設計で方向性2の最初の実装として位置づける。

## 技術的な前提: 個体ごとの売値ボーナス

現在の`itemSellPrice(params, run, id: ItemId)`(`src/lib/game/shidasu/shop.ts`)は、`params.talismans[id].rarity`から一律の売値(C=4/U=8/R=15、`params.shop.itemPrice`)を算出するのみで、護符の個体(instance)ごとの状態を一切持たない。「自分自身の売値を増加させる」効果を実現するには、個体ごとに増加分を保持する仕組みが必要になる。

このセッションで先行実装した`HeldItem = { instanceId: number; id: ItemId }`(`src/lib/game/shidasu/types.ts`)を土台に、以下を追加する:

- `HeldItem`に`sellBonus?: number`を追加する(未定義または省略時は0扱い)。この効果を持つ護符のみが実際に値を持ち、それ以外の護符では常に0のまま。
- `itemSellPrice`のシグネチャを`itemSellPrice(params: ShidasuParams, run: RunState, id: ItemId, sellBonus: number = 0): number`に変更し、`Math.round(priceConfig.sell * multiplier) + sellBonus`を返すようにする(倍率は基礎売値のみに適用し、`sellBonus`は倍率の影響を受けない生の加算値として扱う)。
- 呼び出し元(`engine.ts`の`sellItem`・`mitsu`天啓のトータル計算)は、対象の`HeldItem.sellBonus ?? 0`を第4引数として渡すよう更新する。
- 新規護符自身の効果適用箇所(`itemActualEffects.ts`または新設の専用モジュール)は、トリガー条件を満たした際に`run.items`内の該当インスタンスの`sellBonus`を`+=N`する。

### 蓄積方式: 永続・上限なし

`sellBonus`はラン開始時に0からスタートし、その護符が売却される(=`HeldItem`ごと配列から取り除かれる)まで、Wave・ステージをまたいで永続的に加算され続ける。上限は設けない。これは既存の献身(`dedicationX`)・勤勉(`diligenceX`)・加護(`divineProtectionX`)が採用している「トリガーのたびに`+=0.01`ずつ永続蓄積・上限なし」という設計思想と同じ方針であり、新規の設計原則ではなく既存パターンの踏襲である。

1トリガーあたりの加算量`N`は、既存の護符の売値ベース(C=4/U=8/R=15)に対して小さく(+1〜+5)抑える。ラン終盤には十分な回数のトリガーが蓄積し、育てた護符を高値で売却する、または売らずに長期保有するという選択が生まれる設計を意図している。

## 護符一覧(方向性1: 24件中20件)

### 絞り込みの判断

- **特定1枚のカード**(♠A・♥K・♦J・♣Q、候補5・10・11・12): 4つとも採用する。この種の「スート×ランク1点」トリガーは既存98護符に前例が無い新規パターンで、4スート分揃えることで既存の「スート単体4種」(春風・夏風・秋風・冬風)と対になる自然な構成になる。
- **パターン+閾値m**(同スート・同色・階段・交互、候補14〜17): 4つ全ては採用せず、**階段・交互の2つに絞る**。既存の「役・パターン成立状況」グループが既に5個(恩寵・集中・瑠璃・翡翠・無心)あり、これ以上の水増しを避けるため。
- **役成立**(ロイヤルセット・同ランク・コンプリートラン・ペア、候補18〜21): 4つ全ては採用せず、**ロイヤルセット・コンプリートランの2つに絞る**。理由は上記と同じ。
- **コンボ3段階**(候補2a/2b/2c): 3つとも採用する。既存の「グループ3: 現在のコンボ数判定」内の暁(c=3)・朝霧(c=6)・黄昏(c=10)と直接対応する設計のため、絞り込みの対象にしない。

### エッジトリガーの明確化

「コンボがCに到達するたび」「場札がm枚以下になるたび」のような閾値系トリガーは、既存護符(兆し・三日月など)のような「条件を満たしている間ずっと効果が続く」継続判定ではなく、**その条件を初めて満たした瞬間のみ1回発動する**エッジトリガーとして実装する(そうしないと同一条件下で1プレイごとに何度も発動し、売値が際限なく伸びてしまうため)。「コンボがCに到達した瞬間」は、そのコンボ(直近のリセットからの連続)中でC以上になった最初のプレイでのみ発動し、コンボがリセットされて再度C以上に達すれば再度発動する。

### 「カードプレイ15回以下でWaveクリア」の判定方式

`決算`のみ、他の候補と異なりプレイ中に都度発動するのではなく、Wave終了時点で事後判定する(そのWave中のプレイ回数を数えておき、Waveクリア確定時に15回以下であれば`sellBonus += 5`する)。プレイ回数のカウントは`WaveState`に新規フィールド`playCountThisWave: number`を追加して`playCard`実行のたびにインクリメントする方式を想定する(`drawStock`=山札めくりはカウントに含めない)。`playCountThisWave`は`startWave`で0に初期化し、Wave単位でリセットする。

## 護符一覧(方向性非依存→方向性2扱い: 8件中4件)

### 絞り込みの判断

- 候補2(Wave終了時、全アイテムの売値を一律+=N)は、**除外1**(招き猫・開運こけしが既に全アイテム一律の売買価格操作を担っている)と直接重複するため不採用とする。
- 候補5・6・7(いずれもWave終了時に星片を得る)は、**除外2**(数珠・千社札・算盤が既にWaveクリア時の追加報酬を担っている)と直接重複するため不採用とする。
- 残る候補1・3・4・8は、いずれも「プレイ中の特定条件で星片を即座に獲得する」という方向性2の定義そのものであり、そのまま方向性2の最初の効果候補として採用する。

### 一覧

| 名前 | トリガー | 効果 | rarity |
|---|---|---|---|
| 配当 | 星の妨害行動が発動するたび | 星片+=3 | C |
| 賞金 | ランクLのカードをプレイするたび(LはWaveごとにランダム) | 星片+=1 | C |
| 僥倖 | J・Q・Kのいずれかをプレイしたとき | 25%の確率で星片+=2 | U |
| 祝儀 | 役Yが成立するたび(YはWaveごとにランダム) | 星片+=2 | C |

### ランダム対象(L・Y)の決定タイミング

`賞金`のランクL・`祝儀`の役Yは、Wave開始時(`startWave`)に一様ランダムで1つ確定し、そのWave中は固定する。**個体(instanceId)ごとに独立して保持する**(同名護符を複数所持していても、それぞれ別のL・Yを引く)。このセッションで先行実装したinstanceIdの設計思想(個体ごとに状態を持つ)に沿った方針であり、`HeldItem`にこの2護符専用の`randomTarget?: RoleName | Rank`のようなフィールドを追加する想定。`startWave`実行時、`run.items`内で`賞金`・`祝儀`のinstanceIdごとにランダム値を再抽選し書き戻す処理を追加する。

## 未確定事項

- `決算`の判定閾値「15回以下」は初期値の目安であり、実際のWave中の標準的なプレイ回数(デッキ枚数・場札配布枚数に依存)を踏まえて実装時に調整可能性がある。既存の数値パラメータと同様、`params.talismans`経由で`/admin/shidasu-talismans`から編集可能にする。
- `僥倖`の確率25%は初期値の目安。同様に`/admin/shidasu-talismans`から編集可能にする。

## スコープ外

- 方向性3(秘儀・天啓・神託使用時にキャッシュバック)の効果候補検討・実装は本設計の対象外。別セッションで検討する。
- 方向性1で絞り込んだ「同スート・同色」(候補14・15)、「同ランク・ペア」(候補19・21)は不採用のまま。将来的に護符の総数を増やす際の追加候補として`docs/shidasu/shidasu-reward-talismans-candidates.md`に記録を残す。
- 「ワンパン軸の護符」(ロードマップ項目1のもう一つの検討事項)は対象外。
- 護符総数の最終目標150枚(現状98枚)に対し、本実装で122枚になる。残り28枚は別セッションで検討する。
