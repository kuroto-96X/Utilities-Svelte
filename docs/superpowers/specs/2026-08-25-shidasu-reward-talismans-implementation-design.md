# 報酬増加系護符 実装設計

## 背景・目的

`docs/shidasu/shidasu-reward-talismans-candidates.md`で検討してきた報酬増加系護符の候補のうち、方向性1(特定行動で自分自身の売値を増加、22候補)と、方向性に依存しない候補(8候補)の**全候補32件**を実装する。当初は「役・パターン成立状況グループの水増しを避ける」目的で一部候補を絞り込む案だったが、レビューの結果、絞り込み対象だった4件(候補14・15・19・21)、および既存レリックとの機能重複を理由に除外していた4件(候補2・5・6・7)も含め、方向性1・方向性非依存の候補すべてを採用する方針に変更した。方向性2(プレイ中に特定条件を満たした場合に即時報酬)・方向性3(秘儀・天啓・神託使用時にキャッシュバック)は引き続き未着手だが、方向性非依存候補8件はそのまま方向性2の内容と一致するため、本設計で方向性2の最初の実装として位置づける。

## 技術的な前提1: 個体ごとの売値ボーナス

現在の`itemSellPrice(params, run, id: ItemId)`(`src/lib/game/shidasu/shop.ts`)は、`params.talismans[id].rarity`から一律の売値(C=4/U=8/R=15、`params.shop.itemPrice`)を算出するのみで、護符の個体(instance)ごとの状態を一切持たない。「自分自身の売値を増加させる」効果を実現するには、個体ごとに増加分を保持する仕組みが必要になる。

このセッションで先行実装した`HeldItem = { instanceId: number; id: ItemId }`(`src/lib/game/shidasu/types.ts`)を土台に、以下を追加する:

- `HeldItem`に`sellBonus?: number`を追加する(未定義または省略時は0扱い)。この効果を持つ護符のみが実際に値を持ち、それ以外の護符では常に0のまま。
- `itemSellPrice`のシグネチャを`itemSellPrice(params: ShidasuParams, run: RunState, id: ItemId, sellBonus: number = 0): number`に変更し、`Math.round(priceConfig.sell * multiplier) + sellBonus`を返すようにする(倍率は基礎売値のみに適用し、`sellBonus`は倍率の影響を受けない生の加算値として扱う)。
- 呼び出し元(`engine.ts`の`sellItem`・`mitsu`天啓のトータル計算)は、対象の`HeldItem.sellBonus ?? 0`を第4引数として渡すよう更新する。
- 新規護符自身の効果適用箇所(`itemActualEffects.ts`または新設の専用モジュール)は、トリガー条件を満たした際に`run.items`内の該当インスタンスの`sellBonus`を`+=N`する。

### 蓄積方式: 永続・上限なし

`sellBonus`はラン開始時に0からスタートし、その護符が売却される(=`HeldItem`ごと配列から取り除かれる)まで、Wave・ステージをまたいで永続的に加算され続ける。上限は設けない。これは既存の献身(`dedicationX`)・勤勉(`diligenceX`)・加護(`divineProtectionX`)が採用している「トリガーのたびに`+=0.01`ずつ永続蓄積・上限なし」という設計思想と同じ方針であり、新規の設計原則ではなく既存パターンの踏襲である。

## 技術的な前提2: 数値パラメータの変数化

**効果・rarity内の具体的な数値は、すべて既存98護符と同じ方式で`params.talismans[id]`のフィールドとして変数化し、`/admin/shidasu-talismans`から編集可能にする**(新規admin画面は不要、既存画面がそのまま使える)。既存護符の`{n}`(固定加算量)・`{m}`(枚数閾値)・`{x}`(倍率)・`{c}`(コンボ閾値、暁・朝霧・黄昏で使用中)・`{p}`(確率%、不屈で使用中)という変数命名規則をそのまま踏襲する。以下の一覧表内の数値は**初期値の提案**であり、コード上にハードコードするのではなく、必ず`params.talismans[id].変数名`として実装する。

## 護符一覧(方向性1: 全24件)

### 特定1枚のカード(候補5・10・11・12)

「スート×ランク1点」トリガーは既存98護符に前例が無い新規パターンで、4スート分揃えることで既存の「スート単体4種」(春風・夏風・秋風・冬風)と対になる自然な構成になる。

### パターン+閾値m(候補14〜17)・役成立(候補18〜21)

既存の「役・パターン成立状況」グループが既に5個(恩寵・集中・瑠璃・翡翠・無心)あるため水増しを懸念して4件中2件に絞る案だったが、レビューの結果、方向性1の他の候補と同様に4件とも採用する方針に変更した。

### コンボ3段階(候補2a/2b/2c)

既存の「グループ3: 現在のコンボ数判定」内の暁(`c=3`)・朝霧(`c=6`)・黄昏(`c=10`)と直接対応する設計。

### エッジトリガーの明確化

「コンボが`{c}`に到達するたび」「場札が`{m}`枚以下になるたび」のような閾値系トリガーは、既存護符(兆し・三日月など)のような「条件を満たしている間ずっと効果が続く」継続判定ではなく、**その条件を初めて満たした瞬間のみ1回発動する**エッジトリガーとして実装する(そうしないと同一条件下で1プレイごとに何度も発動し、売値が際限なく伸びてしまうため)。「コンボが`{c}`に到達した瞬間」は、そのコンボ(直近のリセットからの連続)中で`{c}`以上になった最初のプレイでのみ発動し、コンボがリセットされて再度`{c}`以上に達すれば再度発動する。

### 「カードプレイ{c}回以下でWaveクリア」の判定方式

`決算`のみ、他の候補と異なりプレイ中に都度発動するのではなく、Wave終了時点で事後判定する(そのWave中のプレイ回数を数えておき、Waveクリア確定時に`{c}`回以下であれば`sellBonus += {n}`する)。プレイ回数のカウントは`WaveState`に新規フィールド`playCountThisWave: number`を追加して`playCard`実行のたびにインクリメントする方式を想定する(`drawStock`=山札めくりはカウントに含めない)。`playCountThisWave`は`startWave`で0に初期化し、Wave単位でリセットする。

## 護符一覧(方向性非依存→方向性2扱い: 全8件)

候補1・3・4・8はいずれも「プレイ中の特定条件で星片を即座に獲得する」という方向性2の定義そのもの。候補2は除外1(招き猫・開運こけしが担う「全アイテム一律の売買価格操作」)、候補5・6・7は除外2(数珠・千社札・算盤が担う「Waveクリア時の追加報酬」)と機能領域が重複するが、レリックは少数精選・護符は多数の中から個別の小さな効果を組み合わせる設計という位置づけの違いを踏まえ、護符としても実装する方針とした(レビューにより方針変更)。

### ランダム対象(L・Y)の決定タイミング

`賞金`のランクL・`祝儀`の役Yは、Wave開始時(`startWave`)に一様ランダムで1つ確定し、そのWave中は固定する。**個体(instanceId)ごとに独立して保持する**(同名護符を複数所持していても、それぞれ別のL・Yを引く)。このセッションで先行実装したinstanceIdの設計思想(個体ごとに状態を持つ)に沿った方針であり、`HeldItem`にこの2護符専用の`randomTarget?: RoleName | Rank`のようなフィールドを追加する想定。`startWave`実行時、`run.items`内で`賞金`・`祝儀`のinstanceIdごとにランダム値を再抽選し書き戻す処理を追加する。

### `還元`: 秘儀・天啓・神託への影響について(技術的注意点)

`還元`は護符だけでなく秘儀・天啓・神託の売値も底上げする点が他の候補と異なる。対象は「所持している全て」であり、`還元`自身を除外しない(`還元`自身の売値にも`+={n}`が適用される)。現状、秘儀・天啓・神託の売却価格(`riteSellPrice`・`revelationSellPrice`・`oracleSellPrice`)も護符と同様に希少度ベースの一律価格で、個体ごとの状態を持たない。`還元`を実装するには、`itemSellPrice`と同じ要領で`HeldRite`・`HeldRevelation`・`HeldOracle`にもそれぞれ`sellBonus?: number`を追加し、対応する3つの価格関数のシグネチャも`itemSellPrice`と同様に拡張する必要がある。この対応範囲は方向性1の他の候補(護符のみが対象)より広く、実装コストが大きい点に注意する。

### `恩賞`: 蓄積値の保持方式

`恩賞`の星片獲得量は、静的な変数`n`(初期値)・`a`(ステージクリアごとの増加量)とは別に、**個体ごとの現在の蓄積値**を保持する必要がある(`a`はステージクリアのたびに`n`へ加算され続けるため、`n`自体が実行時に変化するランタイム状態になる)。`HeldItem`に`rewardBonus?: number`を追加し、護符取得時に`params.talismans.恩賞.n`で初期化、ステージクリアのたびに`params.talismans.恩賞.a`を加算し、Wave終了時の星片付与量として`rewardBonus`の現在値を使う設計とする。

## 未確定事項

- `決算`の判定閾値`{c}=15`は初期値の目安であり、実際のWave中の標準的なプレイ回数(デッキ枚数・場札配布枚数に依存)を踏まえて実装時に調整可能性がある。
- `僥倖`の確率`{p}=25`%は初期値の目安。
- `褒賞`のランク`{l}`の初期値(l=1、エース)は仮置き。既存の数値パラメータ用の`<input type="number">`をそのまま流用し、1〜13の数値として編集する想定(ランク専用のプルダウン等は用意しない)。
- いずれも既存の数値パラメータと同様、実装後は`/admin/shidasu-talismans`から自由に調整できるため、初期値の細かい妥当性は実装計画作成時・プレイテスト時に見直せばよい。

## スコープ外

- 方向性3(秘儀・天啓・神託使用時にキャッシュバック)の効果候補検討・実装は本設計の対象外。別セッションで検討する。
- 「ワンパン軸の護符」(ロードマップ項目1のもう一つの検討事項)は対象外。
- 護符総数の最終目標150枚(現状98枚)に対し、本実装で130枚になる。残り20枚は別セッションで検討する。
