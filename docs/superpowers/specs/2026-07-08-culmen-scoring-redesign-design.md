# 実装スペック: 登頂ソリティア -Culmen- スコア計算の再設計

## 0. 前提

- 対象: `src/lib/game/culmen/` 配下のスコアリングロジック全般(既存の `engine.ts` / `params.ts` / `culmen.config.json` を変更する)。UIは `src/routes/game/culmen/+page.svelte`、パラメータ調整は `src/routes/admin/culmen/+page.svelte` を必要に応じて拡張する
- 本スペックは `docs/superpowers/specs/2026-07-07-culmen-solitaire-design.md`(初期実装スペック)の後継であり、スコア計算部分(3.3〜3.4節、6章の一部)を置き換える。ゲームの基本ルール(場札の構成、取り合いルール、ウェーブ/ステージ構造、アイテムの種類)は変更しない
- 「点数」を表すパラメータは全て10倍にスケーリングし、コンボ倍率(小数点第1位まで)を掛けても割り切れるようにする。「回数・枚数・閾値・時間」を表すパラメータは変更しない

## 1. コンボ倍率の変更

現行は「獲得点 = 基礎点合計 × コンボ数」(コンボ数そのものを倍率として使用)。これを以下に変更する。

```
comboMultiplierStep (新パラメータ、既定 0.1)
倍率 = 1 + (コンボ数 - 1) × comboMultiplierStep
獲得点 = floor(基礎点合計 × 倍率)
```

- 例(既定値): コンボ1=×1.0、2=×1.1、3=×1.2、8=×1.7
- `floor` は保険。基礎点側を10倍スケーリングしておけば(2節)、`comboMultiplierStep` が小数点第1位までの値である限り常に割り切れるため、通常設定では発火しない
- 倍率の上限キャップは設けない
- 将来「アイテムで `comboMultiplierStep` を加算・上書きする」拡張を見据え、実装時はこのstep値を計算式の直前でローカル変数として取り出しておくこと(例: `let comboMultiplierStep = params.scoring.comboMultiplierStep`)。今回のスコープでは、それを変化させる具体的なアイテムは追加しない

## 2. パラメータの10倍スケーリング

以下の「点数」パラメータの既定値を10倍にする。

| パラメータ | 現行既定値 | 新既定値 |
|---|---|---|
| scoring.basePoint | 10 | 100 |
| scoring.suitBonus | 10 | 100 |
| scoring.colorBonus | 5 | 50 |
| scoring.stairBonus | 15 | 150 |
| scoring.wildSuitBonus | 10 | 100 |
| scoring.clearBonus | 200 | 2000 |
| items.redBonusValue | 5 | 50 |
| items.faceBonusValue | 10 | 100 |
| items.fullClearItemBonus | 300 | 3000 |
| stages[0].targets | [400, 750, 1300] | [4000, 7500, 13000] |
| stages[1].targets | [600, 1100, 1900] | [6000, 11000, 19000] |
| stages[2].targets | [800, 1500, 2600] | [8000, 15000, 26000] |

### 2.1 `/admin/culmen` での一の位固定

上記の「点数」パラメータ(このテーブルの各項目、およびステージ`targets`、6章で追加する役ボーナス各種・`clearBonusPerStock`)は、`/admin/culmen` での編集時に**一の位を常に「0」に固定**した入力欄にする。

- 実際の値を10で割った数値のみを編集可能な `<input type="number">` として表示し、その右側に固定の「0」ラベル(編集不可のテキスト)を添えて全体の値を示す
  - 例: 実際の値が150(`stairBonus`)の場合、入力欄には「15」、その右横に固定表示「0」→ 見た目は「15」+「0」で150
- 保存時は「入力値 × 10」を実際のパラメータ値として `config` に反映する
- `comboMultiplierStep`(既定0.1、点数ではなく倍率のstep)はこの対象に含めない。従来どおり小数点入力(`step="0.1"`)のままとする
- これにより、adminが誤って10の倍数でない値を設定し、コンボ倍率適用時に端数が発生する事態を構造的に防ぐ

変更しないもの(点数ではないため): `scoring.stairMinLen`、`items.shieldChargesPerPick`、`items.extraStockCount`、`items.wildPerPick`、`items.startCombo`、`ui.comboTierThresholds`、`flow.wavesPerStage`、`flow.clearDelayMs`

## 3. パターンボーナスの判定方法の変更(同スート・同色・階段)

現行は「直前に取った1枚とだけ比較するペア判定」(階段は`stairDir`/`stairLen`によるローリングウィンドウで、途中から新しい階段として再成立できる)。これを「**コンボ開始(1枚目)から現在まで、ずっと条件を満たしているか**」の判定に変更する。

- **同スート**: コンボ中に取った実カード(ワイルドを除く)が、コンボ最初の実カードから現在まで**全て同じスート**の場合のみ、取るたびに`suitBonus`を加算。1枚でも異なるスートが入った時点で、そのコンボが終わる(コンボリセット)までこの判定は成立しない
- **同色**: 同様に「全て同じ色(赤/黒)」が条件。同スートとは独立に判定し、同スートが成立していれば同スートを優先(現行同様、両方は同時に加点しない)。「スートはバラバラだが色はずっと同じ」は同色ボーナスの対象になり得る
- **階段**: コンボ最初の実カードから、ランク差±1が**同じ方向に途切れず**続いている場合のみ成立(`stairMinLen`=3枚以上で加算開始)。方向が一度でも崩れたら、そのコンボ中は二度と成立しない(現行の「途中から新しい階段として再スタートできる」仕様を廃止)
- **ワイルド★**: 上記いずれの判定においても「壊さない」素通し役として扱う(同スート・同色の継続を妨げず、階段も方向を維持したまま延長する)。ワイルド自身への無条件`wildSuitBonus`加算は現行どおり維持
- 実装方針: `wave.chain`(コンボ中に取った札の履歴、ワイルド含む)を都度参照し、実カードのみを取り出して各条件の成立を算出する。個々のインクリメンタルなフラグを手動で保持するより、履歴から毎回導出する方が実装がシンプルでバグが出にくい

## 4. 山札めくりでの新コンボ継続ルール

現行、山札をめくった際にコンボが継続するのは「ワイルド★を引いた場合(無条件)」「コンボシールド所持時(得点なし、階段判定のみ継続)」の2パターン。これに加えて、アイテムなしでも以下の場合にコンボを継続できるようにする。

- 捲った札(非ワイルド)が、**現在成立中のパターン(3節の同スート・同色・階段のいずれか)を継続できる**場合、特別にコンボ継続する
  - 例: 同スートが成立中で、捲った札が同じスートなら継続。階段が成立中で、捲った札がその方向を継続していれば継続
  - 成立中のパターンが1つもない状態(既に全て崩れている状態)で捲った場合は、これまで通りコンボリセット
- 捲った札自体には得点を与えない(現行のシールドと同様、次に場から取る札のためのパターン判定基準としてチェーンに加わるだけ)
- この継続が発生した場合、UI側で専用の視覚効果を表示する(具体的な演出内容は実装時に既存のコンボ演出の枠組みに準じて設計してよい。本スペックでは「シールド発動時と区別のつく特別な表示を行う」ことのみを要件とする)

## 5. 全消しボーナスの残り山札連動化

現行は場札が0枚になった時点で `clearBonus` を定額加算するのみ。これを残り山札枚数に応じて加算するよう変更する。

```
clearBonusPerStock (新パラメータ、既定 50)
全消しボーナス = clearBonus + 残り山札枚数 × clearBonusPerStock
             (+「完全消去」所持時は fullClearItemBonus をさらに加算、現行どおり)
```

「残り山札枚数」は全消しが成立した時点(場札を最後の1枚取った直後)の `wave.stock.length` を用いる。

## 6. 役ボーナス(新規スコア軸)

コンボ・全消し・パターンの3軸に加え、「役」という第4の軸を追加する。いずれもコンボ中に取った実カード(ワイルドを除く)の履歴(`wave.chain`)から判定し、対象カードの獲得点計算に加算する(基礎点・アイテムボーナス・パターンボーナスと同様、コンボ倍率適用**前**の合計に加える)。取得時は既存のパターンボーナスと同様、内訳表示(`lastGain.parts`)に含める。

### 6.1 スートコンプリート(フラッシュ)

- 新パラメータ: `scoring.flushBonus`(既定 300)
- 条件: 直近に取った実カード4枚(このカードを含む)が、♠♥♦♣を1枚ずつ含む(順不同)
- 該当するたびに加点(1コンボ中に何度でも成立し得る、直近4枚のスライディングウィンドウで毎回判定)

### 6.2 ロイヤルセット

- 新パラメータ: `scoring.royalSetBonus`(既定 400)
- 条件: 直近に取った実カード3枚(このカードを含む)が、J・Q・Kを1枚ずつ含む(順不同)
- 該当するたびに加点(何度でも成立し得る)

### 6.3 同ランクボーナス

- 新パラメータ: `scoring.sameRankBonusUnit`(既定 100)
- 条件: このカードを取った時点で、現在のコンボ中に**既に取っている同ランクの実カードがM枚**ある場合、`sameRankBonusUnit × M` を加算(M=0なら加算なし)
- 結果として、同ランク2枚目(ペア)で+100、3枚目(スリーカード)でさらに+200(累計300)、4枚目でさらに+300(累計600)、5枚目でさらに+400(累計1000)…と、組み合わせ数(N×(N-1)/2)に比例する形で加速的に増加する
- アイテム等により同一ランクが5枚以上コンボに含まれる場合も、この式でそのまま計算できる

### 6.4 コンプリートラン

- 新パラメータ: `scoring.completeRunBonus`(既定 1000)、`scoring.completeRunSuitBonus`(既定 1000)
- 条件: このカードを取った時点で、現在のコンボ中に取った実カードのランクが1〜13すべて揃った(順不同、重複があってもよい)場合、`completeRunBonus` を加算
- さらに、その揃った13ランク分の実カードが全て同じスートである場合、追加で `completeRunSuitBonus` を加算
- 1コンボにつき最大1回(揃った瞬間の1回のみ。ランクの重複がその後発生しても再加算はしない)

### 6.5 列一掃

- 新パラメータ: `scoring.columnSweepBonus`(既定 150)
- 条件: このカードを取ったことで場札のいずれかの列が完全に空になった場合、それが**現在のコンボ中でK列目に空にした列**であれば `columnSweepBonus × K` を加算
- 同じコンボ内で複数列を空にした場合、列を空にするたびに(2列目なら×2、3列目なら×3というように)加算される
- コンボがリセットされたら列数のカウントもリセットする

## 7. 既存実装との関係

- `evaluatePattern` / `drawStock` の内部実装は、3節・4節の要件を満たすよう見直しが必要(現行の `stairDir`/`stairLen` によるローリングウィンドウ方式から、チェーン履歴を都度参照する方式への変更を含む)
- `playCard` はパターンボーナスに加えて6節の役ボーナスもあわせて計算し、`base` に合算したうえで4節の新コンボ倍率を適用する
- `WaveState` に列一掃のカウント(現在のコンボ中に空にした列数)を保持するフィールドの追加が必要になる見込み
- 既存のテスト(`engine.test.ts`)のうち、スコア計算・パターン判定・山札めくりに関するものは、本スペックの新仕様に合わせて期待値を更新する必要がある
- `src/routes/admin/culmen/+page.svelte` に、新パラメータ(`comboMultiplierStep`、`clearBonusPerStock`、`flushBonus`、`royalSetBonus`、`sameRankBonusUnit`、`completeRunBonus`、`completeRunSuitBonus`、`columnSweepBonus`)の入力欄を追加する。このうち`comboMultiplierStep`以外は2.1節の「一の位固定」入力欄とする。また、既存の点数系パラメータ・ステージ`targets`の入力欄も2.1節の形式に合わせて変更する

## 8. 今回のスコープに含まないもの

- コンボ倍率の上限キャップ(3節で検討したが不採用)
- コンボ倍率stepを変化させる具体的なアイテム(将来検討、今回は拡張しやすい実装構造にするだけ)
- スピード軸(手数・ドロー効率によるボーナス)は不採用
- ステージ制約としての時間制限(将来検討事項としてメモに留める。本スペックでは実装しない)

## 9. 受け入れ基準

1. コンボ8で倍率が×1.7になる(既定`comboMultiplierStep`=0.1の場合)
2. 基礎点100・コンボ倍率1.3倍のとき、獲得点が130(割り切れる)になる
3. 同スートが3枚目で崩れた場合、4枚目以降そのコンボ中は同スートボーナスが二度と付かない(たとえ4枚目・5枚目が同じスートでも)
4. 階段が2枚目で成立し3枚目で方向が反転した場合、4枚目以降そのコンボ中は階段ボーナスが二度と成立しない
5. コンボシールドなしでも、成立中のパターン(同スート等)に合う札を山札から捲るとコンボが継続し、得点は付かない
6. 成立中のパターンが1つもない状態で山札を捲ると、通常どおりコンボがリセットされる
7. 全消し時、残り山札が10枚ならボーナスに`clearBonusPerStock`×10が上乗せされる
8. 直近4枚が4スート全部を含む(順不同)場合、`flushBonus`が加算される
9. 直近3枚がJ・Q・Kを含む(順不同)場合、`royalSetBonus`が加算される
10. 同ランクを2・3・4・5枚と取った場合、各時点での加点が100/200/300/400(累計100/300/600/1000)になる
11. コンボ中に1〜13の全ランクを揃えると`completeRunBonus`が加算され、さらに全て同じスートなら`completeRunSuitBonus`も加算される
12. 1コンボ中に場札の列を2つ空にした場合、1列目で`columnSweepBonus`×1、2列目で`columnSweepBonus`×2が加算される
13. `/admin/culmen`で点数系パラメータ(例: `stairBonus`)の入力欄が「編集可能な数値」+「固定表示の0」の組み合わせで表示され、編集欄に15と入力すると実際の値が150として保存される
14. `npm run test` が全件PASSし、`npm run build` が成功する
