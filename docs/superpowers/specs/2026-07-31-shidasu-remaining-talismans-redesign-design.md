# 未実装護符(グループ18〜22)の再設計 設計

## 背景・目的

`docs/shidasu/shidasu-gofu-candidates.md`は護符100個の効果案を検討したリストで、うち87個(グループ0〜17)は既に実装済み。残るグループ18〜22の13個は「判定ロジック自体の書き換え」「デメリット付き」「専用UI」「他カテゴリ依存」など実装が複雑な効果ばかりで、後回しにされたまま未実装となっている。

今回、この13個についてバランス・面白さの観点から内容を再検討し、実装しやすく差別化された効果へ作り直す。

## スコープ

対象: グループ18〜22の13個(献身・勤勉・加護・紅蓮・漆黒・誓約・契り・白銀・鋼鉄・剛毅・果断・星霜)。加えて、既存実装済みの「水鏡」(`mirror`、グループ17)の名前を「鋼鉄」に変更する(名前の入れ替えのため)。

対象外: グループ0〜17(実装済み87個)の効果変更。今回の再検討はグループ18〜22とその周辺(水鏡の名前変更)にとどめる。

## 再検討結果

### 変更なし(7個)

- **紅蓮・漆黒**: 全札を赤/黒として扱う。月光・陽光・誓約などの色条件系護符を強制成立させるイネーブラーとして役割が明確なため維持。
- **誓約・契り・白銀**: デメリット付き倍算(取れる札の制限・色スート非表示)。バランス調整は実装時のパラメータ(倍率x)で取ればよく、設計自体は維持。
- **果断・星霜**: 秘儀・天啓・神託の使用回数に応じて累積スケーリングする効果。設計は維持。

### 効果を新規に作り直す(5個)

いずれも既存の`ItemId`が未割当のため、新規追加として実装する。

| 護符 | 新効果 |
|---|---|
| 献身 | x点倍算。xは1から開始し、この護符を所持してからフラッシュが成立するたびx+=n(nはパラメータ、既定値0.01)。役成立のたびに永続的に倍率が積み上がる累積型 |
| 勤勉 | x点倍算。xは1から開始し、この護符を所持してから同ランク役が成立するたびx+=n(nはパラメータ、既定値0.01) |
| 加護 | x点倍算。xは1から開始し、この護符を所持してからロイヤルセットが成立するたびx+=n(nはパラメータ、既定値0.01) |
| 剛毅 | Wave開始時、その時点の山札+場札の合計枚数(ワイルド含む実際の総カード枚数)がn枚ごとに、基礎コンボ数(グループ17の「祝福」で導入済みの概念)+1する(nはパラメータ、既定値30)。例: n=30のとき、30〜59枚なら+1、60枚以上なら+2 |
新規護符A(名前は「水鏡」、詳細は次節) | 護符の並び順(ショップ画面の並べ替えUIで変更可能な`run.items`の順序)で、自分の左隣にある護符の効果を、この護符の効果として追加でもう一度発動させる。自分が先頭(左端)の場合、対象となる左隣の護符が存在しないため何も発動しない |

献身・勤勉・加護は同じ「役成立ごとの累積倍算」という型を、それぞれ異なる役(フラッシュ・同ランク・ロイヤルセット)に割り当てる。コンプリートラン・列一掃は既存の護符(謙虚・寛容・治癒・闘志等)で役に依存する効果が既にあるため、対象役から外す。

### 名前の入れ替え(既存護符`mirror`に関わる変更)

- 既存の`mirror`(現在の名前「水鏡」、効果: 役ボーナス成立のたびコンボ中1回、次のプレイで同じ役ボーナスを追加でもう一度加算する)の名前を「**鋼鉄**」に変更する。効果(ロジック)自体は変更しない。
- 上表の新規護符A(左隣の護符効果をもう1回発動)には、「**水鏡**」という名前を割り当てる。

つまり最終的に、「水鏡」という名前を持つ護符は新規護符A(左隣の護符効果をもう1回発動)を指すようになり、「鋼鉄」という名前を持つ護符は既存`mirror`(役ボーナスの次コンボへの遅延コピー)を指すようになる。名前とIDの対応が入れ替わるだけで、`mirror`自体のIDやロジックは変更しない。新規護符Aには新しい`ItemId`(例: `waterMirror`等、実装時に確定)を割り当てる。

## 設計メモ(実装時の留意点)

- 献身・勤勉・加護は、`ItemEffectContext.chainBonus`(成立した役ボーナスの内訳)を参照し、成立した役の種類に応じて護符ごとの内部倍率カウンタ(x)を加算する。カウンタの永続化は、既存の「祝福」の基礎コンボ数のような、`RunState`に新規フィールドを追加する方式を想定する(護符IDごとに独立したカウンタを持つ必要がある)。
- 剛毅は「Wave開始時」に発動するため、`beginRun`/`resolveWaveEnd`後のWave開始処理(`startWave`相当)に処理を追加する必要がある。既存の「祝福」(役成立時に基礎コンボ数+1)とは異なるタイミングでの基礎コンボ数操作になる点に注意。
- 水鏡(新、左隣護符の効果複製)は、`itemEffects.ts`の`applyItemEffects`が`items.reduce`で配列を左から順に適用する既存実装に手を入れる必要がある。「左隣」は`run.items`配列のインデックスで判定し、自分のインデックスが0の場合は何もしない。左隣の護符が「鋼鉄」(遅延コピー系、状態を持つ効果)だった場合の相互作用など、実装時に既存の効果適用ロジックとの整合を個別に検討する。

## テスト方針

実装計画(次のフェーズ)で、各護符ごとに`engine.test.ts`へのユニットテストを追加する。このspecの段階では、効果内容の確定のみを行い、テストケースの詳細は実装計画で定める。
